SigMApy Core Concepts & Architecture

This document provides an overview of the core classes and architectural design of the sigmapy library. Understanding these components can help users leverage SigMApy more effectively, customize its behavior, and contribute to its development.

High-Level Workflow​

The typical workflow in SigMApy involves the following stages:

  1. Input Data Preparation: Mutation data, often from MAF files, VCF files, or pre-compiled CSV count matrices, is loaded and transformed into a standardized Matrix object. This matrix typically contains counts of mutations for each sample across 96 trinucleotide contexts (e.g., C>A in ACA, C>A in ACC, etc.).

  2. Pipeline Configuration: A PipelineConfig object is created to specify various parameters for the analysis. This includes selecting reference signature catalogs, defining the type of sequencing data, specifying the tumor type, and enabling/disabling specific analyses like MVA (Machine Learning-based Variant Analysis) or MSI (Microsatellite Instability) status detection.

  3. Pipeline Construction: A Pipeline object is instantiated using the prepared Matrix and PipelineConfig. The pipeline is composed of a sequence of PipelineStep objects. Users can rely on a default set of steps or customize the pipeline by adding, removing, or reordering steps, including custom-defined steps.

  4. Pipeline Execution: The Pipeline.run() method is called. This executes each PipelineStep in sequence. Each step performs a specific task, such as:

    • Calculating cosine similarity to known signatures.
    • Decomposing mutation spectra into signature exposures (attributing mutations to signatures).
    • Predicting signature activity using machine learning models.
    • The output of one step can be used as input or context for subsequent steps. Intermediate and final results are accumulated within the Pipeline object.

  5. Results Interpretation: The run() method returns a pandas.DataFrame containing the aggregated results from all executed steps. This output can then be used for downstream analysis, visualization, and biological interpretation.

This modular design allows for both standardized analyses and highly customized workflows to suit various research needs.

Core Classes In-Depth​

The functionality of SigMApy is built around a few central classes. Understanding their roles and interactions is key to using the library effectively.

Matrix​

The Matrix class (found in sigmapy.utils.Matrix) is the primary input data container in SigMApy. It encapsulates the mutational count data for one or more samples.

Role:

  • Represents the input SNV (Single Nucleotide Variation) spectra, typically as counts of mutations across 96 trinucleotide contexts (e.g., A[C>A]A, A[C>A]C, ..., T[T>G]T).
  • Can also hold other sample-related information or features if added.
  • Provides a standardized format for pipeline steps to consume.

Instantiation: A Matrix object can be created in several ways:

  1. From a MAF (Mutation Annotation Format) file:

    from sigmapy.utils import Matrix
    matrix = Matrix(input="path/to/your/data.maf", ref_genome="path/to/your/hg19_genome.fa")

    This is a common starting point. SigMApy will process the MAF file to count mutations in their respective trinucleotide contexts. A reference genome is required to determine these contexts.

  2. From a VCF (Variant Call Format) file: Support for VCFs might also be available, often requiring similar context generation using a reference genome. (Consult Matrix class documentation for specifics if directly supported or if conversion to MAF/CSV is preferred).

  3. From a CSV file: If you have a pre-computed matrix where rows are samples and columns represent the 96 mutation channels (and potentially other metadata), you can load it directly.

    matrix = Matrix(input="path/to/your/mutation_counts.csv")

    The CSV should have samples as rows and mutation types (e.g., "ACAA", "ACAC", or "A[C>A]A") as columns.

  4. From a pandas DataFrame: You can also create a Matrix object from an existing pandas DataFrame.

    import pandas as pd
    # Assuming `my_dataframe` is correctly formatted (samples as index or a specific column, 96 channels as columns)
    matrix = Matrix(input_df=my_dataframe, sample_col='SampleID') # if samples are in a column
    # OR: if samples are in the index
    matrix = Matrix(input_df=my_dataframe)

Key Attributes/Properties:

  • matrix.df: A pandas.DataFrame that holds the actual data.
    • Typically, the index of this DataFrame represents sample IDs.
    • Columns include the 96 mutation channels (e.g., A[C>A]A, A[C>A]C, ... or similar nomenclature).
    • May also include other metadata columns like total_snvs, tumor type, etc., either loaded initially or added during processing.
  • Validation: The Matrix class performs some validation upon initialization to ensure the data is in a usable format (e.g., checking for the presence of expected channel columns).

The Matrix object is passed to the Pipeline and is accessible by each PipelineStep via self.pipeline.matrix.

PipelineConfig​

The PipelineConfig class (found in sigmapy.core.PipelineConfig) is responsible for holding all the configuration settings for a SigMApy pipeline run. It allows users to customize various aspects of the analysis.

Role:

  • Acts as a centralized container for all pipeline parameters.
  • Ensures that all parts of the pipeline (and individual steps) have consistent access to user-defined settings.
  • Can perform validation or preprocessing of configuration values.

Instantiation: A PipelineConfig object is created by providing values for its various parameters.

from sigmapy.core import PipelineConfig

config = PipelineConfig(
    catalog="cosmic_v3_sbs",     # Name of the signature catalog to use
    seq_type="wgs",              # Type of sequencing data (e.g., "wgs", "seqcap", "op_multisig")
    tumor_type="Breast-AdenoCa", # Specific tumor type for context-specific analysis
    cutoff=5,                    # Minimum number of mutations to consider a sample for some analyses
    mva=True,                    # Whether to run MVA (Machine Learning-based Variant Analysis) steps
    assign=True,                 # Whether to assign samples to signatures based on thresholds
    msi=False,                   # Whether to include MSI (Microsatellite Instability) specific steps/signatures
    wcf=False,                   # Weighted Cluster Fraction: specific weighting for some models/steps
    lite=False,                  # Run in "lite" mode (may alter behavior of some steps for speed)
    de_novo_sig3=False,          # Special handling for de novo Signature 3
    norm96=None,                 # Optional custom normalization factors for the 96 channels
    readjust=False,              # Whether to readjust samples below cutoff (specific use case)
    verbose=0                    # Verbosity level (0: silent, 1: basic info, 2: detailed info)
)

Common Configuration Parameters:

  • catalog (str): The name of the reference signature catalog to be used (e.g., "cosmic_v2_inhouse", "cosmic_v3_sbs"). SigMApy usually looks for a corresponding .csv file in its reference data directory.
  • seq_type (str): Specifies the sequencing platform or data type (e.g., "wgs" for Whole Genome Sequencing, "seqcap" for capture-based sequencing, "msk" for MSK-IMPACT data, "op_multisig" for specific operational multi-signature contexts). This can affect normalization and which signatures or models are applicable.
  • tumor_type (str): The type of tumor being analyzed (e.g., "breast", "lung_scc", "other"). This is often used to select tissue-specific signatures or apply relevant cutoffs.
  • cutoff (int): A threshold, typically the minimum number of SNVs a sample must have to be included in certain calculations or assignments.
  • mva (bool): If True, enables steps that use Machine Learning-based Variant Analysis (MVA) for signature prediction or scoring (e.g., MVAStep).
  • assign (bool): If True, enables logic in some steps (like MedianCatalogStep or MVAStep) to make a binary call (pass/fail) for signature presence based on calculated scores and predefined cutoffs.
  • msi (bool): If True, specialized steps and signatures related to Microsatellite Instability (MSI) might be included in the pipeline.
  • wcf (bool): "Weighted Cluster Fraction." A boolean flag that can modify the behavior of certain catalog matching or MVA steps, often relevant for specific data types like MSK-IMPACT when mva is true.
  • lite (bool): If True, might trigger a "lite" mode in some steps, potentially simplifying calculations or using smaller models for faster execution, possibly at the cost of some precision.
  • de_novo_sig3 (bool): A flag for special handling of "Signature 3" (associated with BRCA deficiency), particularly if it's being considered as a de novo signature or needs specific components from a catalog.
  • norm96 (object, often array-like): Allows providing custom normalization factors for the 96 trinucleotide channels. If None, default normalizations based on seq_type or other factors might be applied.
  • readjust (bool): If True, samples that fall below the cutoff might be handled differently (e.g., retained in a separate list rather than being completely discarded).
  • verbose (int): Controls the amount of informational output during the pipeline run (0 for minimal, higher for more details).

The PipelineConfig object is stored as self.pipeline.config and is accessible by all pipeline steps, allowing them to tailor their behavior based on these global settings.

PipelineStep and Built-in Steps​

The PipelineStep class (found in sigmapy.base.PipelineStep) is the abstract base class for all operations performed within a SigMApy Pipeline. Each distinct analytical action is implemented as a class inheriting from PipelineStep.

Role of PipelineStep:

  • Defines a common interface for all steps in a pipeline.
  • Encapsulates a specific piece of logic (e.g., data transformation, calculation, model prediction).
  • Manages its own state and access to global pipeline data (like self.pipeline.matrix, self.pipeline.config, self.pipeline.signatures, and self.pipeline.output).

Lifecycle Methods: As detailed in the "Creating Custom Pipeline Steps" guide, key methods include:

  • __init__(self, ..., pipeline=None): Constructor.
  • preprocess(self): Preparatory work before run().
  • run(self): Core execution logic, produces self.output.
  • postprocess(self): Integrates self.output into self.pipeline.output.

Built-in Steps: SigMApy comes with several pre-defined steps (mostly inheriting from sigmapy.base.PipelineInbuildStep, which itself inherits from PipelineStep) that perform common signature analysis tasks. These are added to a pipeline by default or can be added conditionally based on the PipelineConfig. Here are a few examples:

  • MedianCatalogStep:

    • Purpose: Matches samples against a "median" or "average" signature catalog, often specific to a tumor type. It calculates likelihoods or scores indicating how well each sample's mutation spectrum matches the profiles in this average catalog.
    • Key Action: Computes matching scores using CatalogMatcher.match_median_catalog(). Can also handle assignment logic if config.assign is true.
    • Output: DataFrame with scores/assignments for signatures in the median catalog.

  • CosineSimilarityStep:

    • Purpose: Calculates the cosine similarity between each sample's mutation spectrum and each signature profile in a given reference catalog (e.g., COSMIC).
    • Key Action: Uses CatalogMatcher.match_cosine_similarity().
    • Output: DataFrame with cosine similarity values for each sample against each signature.

  • DecomposeStep:

    • Purpose: Decomposes (or "deconstructs") the mutation spectrum of each sample into a set of exposures to known signatures. This typically involves solving a non-negative least squares (NNLS) problem to find the optimal contribution of each signature to the observed spectrum.
    • Key Action: Uses CatalogMatcher.decompose().
    • Output: DataFrame where rows are samples and columns are signatures, with values representing the estimated number of mutations (exposures) attributed to each signature in each sample.

  • WeightedCatalogStep:

    • Purpose: Similar to MedianCatalogStep but may use a weighted approach for matching against a catalog, often used in specific contexts (e.g., for breast cancer analysis in the default pipeline).
    • Key Action: Uses CatalogMatcher.match_weighted_catalog().
    • Output: DataFrame with scores from the weighted catalog matching.

  • MVAStep:

    • Purpose: Implements Machine Learning-based Variant Analysis (MVA). It uses pre-trained machine learning models to predict the activity or likelihood of certain signatures (often complex ones like HRD-related Signature 3 or MSI signatures).
    • Key Action: Uses MVAPredictor.predict(). Can also handle assignment based on model scores if config.assign is true.
    • Output: DataFrame with MVA scores and potentially assignments (e.g., Signature_3_mva, pass_mva).

These steps are added to the Pipeline's steps list and are executed sequentially when pipeline.run() is called. The pipeline.output DataFrame is progressively built up by the postprocess method of each step, typically by concatenating the current step's output DataFrame.

Pipeline​

The Pipeline class (found in sigmapy.core.Pipeline) is the central orchestrator of the analysis workflow in SigMApy. It brings together the input data, configuration, and a sequence of processing steps to produce the final results.

Role:

  • Manages the overall analysis pipeline.
  • Holds references to the PipelineConfig object (pipeline settings) and the Matrix object (input data).
  • Maintains an ordered list of PipelineStep instances that define the operations to be performed.
  • Executes the pipeline steps in sequence and aggregates their outputs.

Instantiation: A Pipeline object is created by providing a PipelineConfig instance and a Matrix instance. Optionally, a custom list of PipelineStep objects can be provided.

from sigmapy.core import Pipeline, PipelineConfig
from sigmapy.utils import Matrix 
# IF using custom stipes
from sigmapy.base import MyCustomStep 
matrix = Matrix(...) 
config = PipelineConfig(...)

# Scenario 1: Using default steps (and steps added based on config)
pipeline = Pipeline(config=config, matrix=matrix)

# Scenario 2: Providing a custom list of steps (rarely needed for initial setup, more for advanced customization)
custom_steps_list = [MyCustomStep(pipeline=None)] # Pipeline reference is set by add_step or internally.
                                                 # It's generally better to use add_step.
pipeline = Pipeline(config=config, matrix=matrix, steps=custom_steps_list) 

# Scenario 3: Initializing with no default steps and adding them manually (Recommended for clarity with custom steps)
pipeline = Pipeline(config=config, matrix=matrix, steps=[]) # Start with an empty list
# Then use pipeline.add_step(StepClass, **kwargs)

If the steps argument is not provided (or is None) during instantiation, the Pipeline constructor typically populates a default sequence of steps (e.g., MedianCatalogStep, CosineSimilarityStep, DecomposeStep). Additional steps (like WeightedCatalogStep or MVAStep) might be added automatically based on settings in the PipelineConfig (e.g., config.tumor_type == "breast" or config.mva == True).

Key Methods and Attributes:

  • pipeline.config: The PipelineConfig instance associated with this pipeline.
  • pipeline.matrix: The Matrix instance (input data) for this pipeline.
  • pipeline.steps: A list of PipelineStep instances that will be executed.
  • pipeline.signatures: Often populated during the preprocess phase of steps, this attribute typically holds the reference signature profiles (as a DataFrame) that are relevant for the current analysis context (e.g., filtered by tumor type, normalized).
  • pipeline.output: A pandas.DataFrame that accumulates the results from each executed PipelineStep. Each step's postprocess method is usually responsible for concatenating its self.output to pipeline.output.
  • pipeline.add_step(step_cls, step="mss", target="Signature_3", catalog="cosmic_tissue", **kwargs):
    • This method is used to add a step to the pipeline.
    • step_cls: The class of the step to be added (e.g., DecomposeStep, MyCustomStep).
    • Other arguments (step, target, catalog, and any additional **kwargs) are passed to the constructor of step_cls.
    • Crucially, add_step instantiates step_cls and passes pipeline=self to its constructor, linking the step to the pipeline instance.
  • pipeline.run():
    • This is the method that executes the pipeline.
    • It iterates through each PipelineStep in the pipeline.steps list.
    • For each step, it typically calls:
      1. step.preprocess()
      2. step.run()
      3. step.postprocess()
    • The method returns the final pipeline.output DataFrame, which contains the combined results of all steps.

The Pipeline class thus provides a structured environment for complex multi-step analyses, ensuring that data and configuration are managed consistently and that results are properly aggregated.

Supporting Components​

Beyond the core classes that define the pipeline structure (Matrix, PipelineConfig, PipelineStep, Pipeline), SigMApy utilizes several other important components to perform its analyses. These are often used internally by the built-in pipeline steps.

CatalogMatcher​

  • Location: sigmapy.catalog_matcher.CatalogMatcher
  • Role: This class encapsulates the logic for various methods of matching sample mutation profiles against reference signature catalogs. It's a key algorithmic component.
  • Functionality Includes:
    • Calculating cosine similarities (match_cosine_similarity()).
    • Decomposing spectra using Non-negative Least Squares (NNLS) (decompose()).
    • Matching against median or weighted catalogs (match_median_catalog(), match_weighted_catalog()).
  • Usage: Instances of CatalogMatcher are typically created and used within specific PipelineSteps (e.g., CosineSimilarityStep, DecomposeStep, MedianCatalogStep). The PipelineStep itself initializes CatalogMatcher often passing genomes=self.pipeline.matrix.df.

MVAPredictor​

  • Location: sigmapy.mva_predictor.MVAPredictor
  • Role: Handles predictions using pre-trained Machine Learning (ML) models, a core part of the MVA (Machine Learning-based Variant Analysis) functionality.
  • Functionality Includes:
    • Loading ML models (often gradient boosting models like XGBoost or LightGBM) from files.
    • Preparing input data (which can be a combination of mutation counts and outputs from previous pipeline steps) for these models.
    • Making predictions (predict()) which could be scores, probabilities, or class labels related to signature activity.
  • Usage: An instance of MVAPredictor is typically created and used within the MVAStep. The step provides the necessary input DataFrame (often pd.concat([self.pipeline.matrix.df, self.pipeline.output], axis=1)) to the predictor.

sigmapy.utils​

  • Location: This is a package (sigmapy/utils/) containing various utility modules.
  • Role: Provides a collection of helper functions and constants that support the core operations of SigMApy.
  • Key Modules and Functionality:
    • sigmapy.utils.data: Functions for loading reference data, catalogs (e.g., get_catalog()), and other necessary resources.
    • sigmapy.utils.matrix: Contains the Matrix class itself and related matrix operations.
    • sigmapy.utils.constants: Defines various constants used throughout the library (e.g., paths to reference files, predefined lists of signatures).
    • sigmapy.utils._utils: General utility functions that don't fit into a more specific category.
    • sigmapy.utils.strings: String manipulation utilities, if any.
  • Usage: These utility functions are imported and used as needed by different classes and methods throughout the sigmapy library to avoid code duplication and centralize common tasks. For example, PipelineConfig uses get_config() (likely from utils) to find paths, and steps use _utils.get_catalog() to load signature definitions.

Understanding that these components exist and their general purpose can be helpful when tracing data flow or debugging, even if you don't interact with them directly when using the standard pipeline.

Overall Architecture and Data Flow​

The architecture of SigMApy is designed to be modular, allowing for a flexible and extensible system for mutational signature analysis. Here's how the core components generally interact:

1. Initialization Phase:

  • User Input: The process starts with user-provided mutation data (e.g., MAF file, CSV matrix) and analysis preferences.
  • Matrix Creation: The input data is loaded into a Matrix object (pipeline.matrix). This standardizes the format of the mutation counts and associated sample information.
  • PipelineConfig Creation: User preferences are encapsulated in a PipelineConfig object (pipeline.config). This object holds all settings that will guide the pipeline's behavior.
  • Pipeline Instantiation: A Pipeline object is created, taking the matrix and config as arguments.
    • During its initialization, the Pipeline may populate its steps list with a default sequence of PipelineStep instances.
    • It also conditionally adds other built-in steps based on the config (e.g., MVAStep if config.mva is true, WeightedCatalogStep for certain tumor types).
    • Users can further customize this steps list using pipeline.add_step() to include custom steps or modify the sequence. Each step instance passed to add_step (or created internally) receives a reference to the pipeline itself, allowing it to access shared data and configuration.

2. Execution Phase (pipeline.run()):

  • The pipeline.run() method iterates through each PipelineStep in its pipeline.steps list.
  • For each step:
    • step.preprocess():
      • The step prepares for execution.
      • It can access self.pipeline.matrix (for input data), self.pipeline.config (for settings), and self.pipeline.signatures (which might have been prepared by a previous step or an initial setup phase, often involving loading and filtering reference signatures based on config.catalog, config.tumor_type, and config.seq_type).
      • The PipelineInbuildStep's preprocess method, for example, handles complex logic for selecting and normalizing signatures from the loaded catalog based on various config parameters.
    • step.run():
      • This is the core execution method where the step performs its specific analysis (e.g., similarity calculation, decomposition, MVA prediction).
      • The step may utilize components like CatalogMatcher or MVAPredictor, providing them with data from self.pipeline.matrix.df and/or self.pipeline.output (results from previous steps), and using signatures from self.pipeline.signatures.
      • The result of the step's computation is stored in step.output (usually a pandas DataFrame).
    • step.postprocess():
      • The step integrates its step.output into the main pipeline.output DataFrame.
      • Typically, this involves concatenating step.output to pipeline.output along axis=1 (i.e., adding new columns). Care is taken to handle potentially overlapping column names or indices. The base PipelineStep.postprocess method provides default concatenation logic.

3. Data Flow Summary:

  • Initial Input: Matrix.df contains the primary mutation count data.
  • Reference Signatures: Loaded based on PipelineConfig.catalog and filtered/normalized based on seq_type, tumor_type, etc., stored in pipeline.signatures (accessible as step.signatures).
  • Step-wise Processing:
    • Each step reads from pipeline.matrix.df, pipeline.signatures, and potentially pipeline.output (from prior steps).
    • Each step writes its results to its own step.output.
  • Accumulated Output: pipeline.output starts as None or an empty DataFrame. After each step's postprocess, pipeline.output is updated to include the new results.
  • Final Output: The pipeline.run() method returns the final pipeline.output DataFrame, which contains a wide table with the original sample information (often from the index of pipeline.matrix.df) and all the results (columns) generated by the executed steps.

Conceptual Diagram:

[User Data (MAF/CSV)] -> Matrix_Object ([matrix.df])
                                |
                                V
[User Settings] -> PipelineConfig_Object ([config])
                                |
                                V
                Pipeline_Object.run()
                (manages [matrix], [config], [steps_list], [output_df (initially None)])
                        |
                        |--> For each Step_Object in [steps_list]:
                        |       1. step.preprocess() (uses [matrix], [config], prepares/accesses [pipeline.signatures])
                        |       2. step.run() (uses [matrix], [config], [pipeline.signatures], [pipeline.output from prev. steps])
                        |                       (may use CatalogMatcher, MVAPredictor)
                        |                       (generates step.output)
                        |       3. step.postprocess() (merges step.output into pipeline.output_df)
                        |
                        V
                [Final output_df] (returned by pipeline.run())

This architecture emphasizes separation of concerns: data representation (Matrix), configuration (PipelineConfig), operational units (PipelineStep), and orchestration (Pipeline), making the system robust and adaptable.

Codebase Structure (A Brief Note)​

For users interested in navigating the SigMApy codebase itself, here's a simplified guide to where key components are generally located within the main sigmapy package:

  • sigmapy/
    • core.py: Contains the central orchestrating classes:
      • Pipeline
      • PipelineConfig
    • base.py: Defines the base class for all pipeline operations and includes many common built-in steps:
      • PipelineStep (base class)
      • PipelineInbuildStep (intermediate base for built-in steps)
      • Specific steps like MedianCatalogStep, CosineSimilarityStep, DecomposeStep, WeightedCatalogStep, MVAStep.
    • catalog_matcher.py:
      • CatalogMatcher class, responsible for various algorithms to match mutation profiles to signature catalogs.
    • mva_predictor.py:
      • MVAPredictor class, which handles loading and using machine learning models for MVA predictions.
    • utils/: This sub-package contains various utility modules:
      • data.py: Functions for loading reference data, catalogs, etc.
      • matrix.py: Contains the Matrix class definition.
      • constants.py: Defines shared constants.
      • _utils.py: General helper functions.
      • (Other utility modules as needed).
    • __init__.py: Makes SigMApy a package and often exports key classes for easier access (e.g., from sigmapy import Pipeline).

This structure helps organize the library by functionality, separating core orchestration, step definitions, specialized algorithmic components, and general utilities.
